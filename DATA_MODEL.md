# Модель данных MatchLab

DBML в schema/matchlab.dbml — источник ER-модели, исполняемые миграции находятся в backend. Реализованные сервисы владеют своими схемами. Chat реализован двумя таблицами в схеме chat по миграции backend 00008. Только public.notification остаётся будущей моделью без текущей миграции.

## Владение данными

| Владелец | Таблицы | Назначение |
| --- | --- | --- |
| User | users.user_account, user_email, registration_request | Аккаунты, подтверждённые email и независимые заявки до создания аккаунта. |
| User | users.trusted_email_domain, admin_event | Доменные правила, ревизии и история системных блокировок/правил. |
| User | users.user_profile, achievement, achievement_decision | Профиль, достижения и снимки решений. |
| User | users.user_block, project_context, project_context_member, profile_review | Личные блокировки, проекция команды/состояния проекта, отзывы о людях. |
| Media | media.file, multipart_upload | Метаданные/состояния файлов и multipart; байты хранятся в S3. |
| Support | support.support_ticket, support_ticket_attachment, ticket_event | Жалобы, вложения, назначения и атомарная история. |
| Project | projects.project, role, member, join_request, moderation, context_outbox | Жизненный цикл, роли/места, команды, заявки, аудит и доставка снимков в User. |
| Admin | admin.account, session, login_throttle, audit_event | Независимые сотрудники, служебные сеансы, защита входа и общий аудит. |
| Chat | chat.conversation, message | Личные текстовые диалоги, сообщения и отметки прочтения. |
| Будущие сервисы | public.notification | Планируемые уведомления, без текущего API. |

## Основные инварианты

- Email нормализуется и является единственным логином User. Заявка до подтверждения не резервирует аккаунт; только актуальный токен создаёт user_account и user_email. Письма отправляет Mail синхронно, таблицы писем нет.
- Статус active/blocked/deleted отделён от подтверждения почты и личных блокировок. Служебные аккаунты Admin независимы от публичных профилей и их старых role.
- Разрешённые домены проверяются и перед отправкой письма, и при подтверждении. Изначальные hse.ru и edu.hse.ru добавлены миграцией без перезаписи существующих правил.
- Публикация сразу открывает recruiting. Жизненный цикл: recruiting/unpublished/active/completed/cancelled. Скрытие модератором — отдельный moderation_hidden. При принятии заявок строка проекта блокируется; активные участники не превышают число мест роли.
- Достижения: unverified/pending_review/verified/needs_evidence. Редактирование сбрасывает проверку; история хранит проверенный снимок. Приватное доказательство не становится публичным при одобрении.
- Жалоба содержит ровно одну цель: пользователя или проект. Ticket/file уникальны. Статусы open/resolved/declined; назначение сотрудника хранится отдельно. Каждая мутация и её история атомарны.
- Межсервисные ID не имеют FK; внутри владельца применяются FK с NO ACTION и логическое удаление бизнес-сущностей. Все связи отражены в генерируемой диаграмме README.
- JSONB хранит типизированные описания и снимки. Статусы, акторы, ревизии, вместимость и идентификаторы — отдельные колонки. Пароли, ключи и сеансовые токены не хранятся в JSONB/аудите.
- Инварианты закреплены сервисами и SQL CHECK/уникальностью/транзакциями. После правки DBML генерируйте README и запускайте npm run check перед каждым push/merge.

## Реализованная схема Media

Миграции backend `00002` и `00003` создают схему `media`; DBML отражает их поля, ограничения и индексы. Реализованные схемы User, Support, Project, Admin и Chat описаны ниже; public.notification остаётся целевой сущностью. Служебные таблицы Goose и SQL-отпечатков принадлежат migration runner и не являются продуктовыми сущностями.

Файл проходит `pending → ready`. Проверка HEAD сверяет Content-Type и ожидаемый размер с S3. Отмена multipart переводит файл в `failed`. Только владелец удаляет готовый файл; `deleting` хранит внутреннее намерение, а `deleted` — завершённое удаление. Промежуточное состояние позволяет восстановить операцию после сбоя между двумя системами. Оба состояния скрыты из чтения; публичный API не содержит `deleting`. Запись в БД остаётся, байты удаляет S3 DeleteObject.

Уникальна пара `(bucket_name, object_key)`. Для поиска применяются индекс владельца по времени (DESC), индекс состояния и частичный индекс старых `pending`. `owner_user_id` намеренно не ссылается внешним ключом на таблицу другого сервиса. Значение `is_public` разрешает анонимное чтение через Media, но не открывает сам bucket. ETag не является SHA-256.

Multipart-сессия имеет FK на `media.file`, использует состояния `uploading`, `completing`, `completed`, `aborted`. Manifest частей фиксируется перед завершением, чтобы повтор переживал перезапуск. Размер части — 5 МиБ–5 ГиБ, максимум 10000 частей; `expires_at > created_at`. Частичный индекс просроченных незавершённых сессий поддерживает восстановление. SQL Down удаляет tracking-сессии; незавершённые загрузки в S3 необходимо отменить до отката.


## KAN-38: User ProfileService

- `users.user_profile`: типизированные данные профиля в JSONB и настройки видимости. Создаётся для каждого аккаунта; навыки/интересы индексируются GIN. Значок вычисляется по подтверждённой почте hse.ru/edu.hse.ru, отдельно от достижений.
- `users.achievement`: образование, сертификаты, научные и проектные работы. Файлы ссылаются на Media по ID, без межсервисного FK и постоянных signed URL. Статусы unverified, pending_review, verified, needs_evidence. Редактирование сбрасывает проверку; удаление логическое.
- `users.achievement_decision`: неизменяемая история решений с модератором, версией, снимком проверенных данных, доказательством и комментарием. Владелец не проверяет свои достижения.
- `users.user_block`: направленные блокировки; сервисы сообщений и приглашений проверяют обе стороны. Общие проекты не удаляются.
- `users.project_context` и `users.project_context_member`: минимальный доверенный контекст команды. NULL completed_at означает текущий проект; завершённый снимок неизменяем и позволяет оставить отзыв. Полная модель проекта остаётся отдельной будущей областью.
- `users.profile_review`: один отзыв автора об адресате на завершённый проект. Оба должны быть участниками, оценка 1–5, отзыв о себе запрещён. Средняя оценка вычисляется по отзывам.

Контакты доступны владельцу, текущей команде или публично по настройке; блокировка скрывает их от другой стороны. Флаг видимости участия в проектах сохранён для будущего Projects. С KAN-35 внутренние методы очереди/решений/доказательств требуют подписанной служебной идентичности Admin. HTTP-доступ идёт через отдельный административный фасад.

Миграция 00005 добавляет точные домены hse.ru и edu.hse.ru без изменения существующих правил. Down удаляет новые данные, но сохраняет доменные правила. Исполняемый SQL находится в matchlab-backend; DBML содержит также будущие сущности, ещё не реализованные в API.


## KAN-39: проекты, поиск и рекомендации

- `projects.project` — владелец, типизированное описание JSONB, жизненный цикл и отдельный флаг скрытия модератором. Публикация сразу открывает набор; версия защищает редактирование.
- `projects.role` — роль, навыки, число мест и логическое удаление. Занятость определяется активными участниками, при принятии заявок блокируется проект.
- `projects.member` — состав с состояниями active/left/removed. Инициатор имеет NULL role_id. После завершения состав замораживается.
- `projects.join_request` — отклики и приглашения на роль. Одна pending-заявка на роль/кандидата; решения проверяют вместимость и полномочия принимающего.
- `projects.moderation` — аудит скрытия/восстановления с актором и обязательной причиной. Методы доступны только внутренним административным RPC.
- `projects.context_outbox` — снимки команды/жизненного цикла, атомарные с изменением проекта. Доставка в User повторяется; credentials в payload не хранятся.

Миграция backend 00006 добавляет Project и source_revision/state в `users.project_context`. User применяет только новые версии: текущая команда даёт доступ к контактам, отмена прекращает его, завершение разрешает отзывы. Старые события не возвращают удалённого участника и не открывают закрытый проект заново. Это проекция, а не совместное владение таблицами. Project читает профиль и блокировки только через gRPC; межсервисных FK нет.

Search и Recommendation не создают бизнес-таблиц. Поиск выполняется API владельцев User/Project; Recommendation запрашивает случайную выборку доступного множества через Search. Приватные контакты и доказательства в поисковые карточки не включаются. Полноценный внешний индекс и ML-модель — отдельное развитие.

Down 00006 удаляет данные Project, аудит и недоставленные события; текущие/отменённые проекции Project удаляются для отзыва прав на контакты, завершённые снимки и отзывы сохраняются. source_revision/state проекции также удаляются. Исполняемые миграции находятся только в backend.

## Администрирование — KAN-35

Admin владеет отдельной схемой `admin`: `account`, `session`, `login_throttle`, `audit_event`. Служебные аккаунты не являются публичными профилями и не получают права через регистрацию или роли в `users.user_account`. Роли: `moderator` и `administrator`. Первый администратор создаётся операторской командой, остальные — через административный API. Пароли bcrypt, сеансы содержат только SHA-256-хеш криптографического токена; срок — восемь часов. Смена пароля, роли, статуса и принудительный отзыв увеличивают `session_version`, который проверяется при каждом запросе. Последнего активного администратора нельзя отключить или понизить; проверки сериализуются advisory transaction lock.

User владеет блокировкой `user_account.status`, ревизиями аккаунтов и разрешённых доменов, а также `users.admin_event`. Блокировка закрывает защищённые действия по уже выданному пользовательскому сеансу; анонимные возможности сохраняются. Разблокировка возвращает доступ по ещё действующим пользовательским сеансам. Деактивация домена запрещает новую регистрацию и подтверждение ожидающей заявки, существующие аккаунты не блокирует.

Support хранит `assigned_admin_id`, `revision`, `resolution_comment` и `support.ticket_event`. Активная очередь — `open`, с фильтром по назначению; закрытые — `resolved` и `declined`. Можно назначить сотрудника, снять назначение, закрыть, отклонить, вернуть в очередь и оставить внутреннюю заметку. Каждая мутация и её история фиксируются одной транзакцией; `expected_revision` предотвращает потерю параллельных решений. Закрытие и повторное открытие требуют комментария. Закрытие жалобы само по себе не блокирует пользователя и не скрывает проект: это самостоятельные аудируемые решения.

`achievement_decision.reviewer_admin_id` и `projects.moderation.actor_admin_id` указывают на служебные идентичности без межсервисного FK. Старые `reviewer_user_id` / `actor_user_id` остаются для истории; ровно один вид автора обязателен. Новые решения требуют подписанных служебных полномочий Admin. Администратор с тем же email не может рассматривать собственное достижение. Одобрение даёт `verified`, отказ возвращает `needs_evidence` с комментарием и допускает повторную подачу.

Admin обращается к данным только по gRPC владельца. Общий audit записывает намерение до межсервисной операции и её результат; `unknown` означает потерю/неопределённость ответа, а не откат. Авторитетная история мутаций хранится у владельца и атомарна с изменением. Пароли, сеансовые токены, приватные ключи, подписанные URL и тела запросов в общий audit не попадают. Истории и списки имеют стабильную пагинацию и total. Статистика включает текущие распределения состояний и дневную активность UTC за заданный период; единая распределённая транзакция между сервисами не предполагается.

Модель соответствует новой миграции backend `00007`. Опубликованные миграции не меняются. Down отказывается удалять накопленную административную историю: перед откатом оператор должен отдельно сохранить и обработать её. Откат пустой схемы удаляет служебные таблицы и новые поля.

## KAN-37: Chat — личная переписка

Миграция backend `00008_create_chat.sql` создаёт ровно две таблицы. Старые
public.chat_conversation, public.chat_participant и public.message заменены
на `chat.conversation` и `chat.message`.

### chat.conversation

- id — UUID диалога, gen_random_uuid().
- user_low_id / user_high_id — ровно два различных пользователя в каноническом порядке UUID;
  CHECK user_low_id < user_high_id и UNIQUE пары исключают диалог с собой и дубли.
  Межсервисных FK к User нет.
- last_message_seq — последний номер сообщения, bigint >= 0, по умолчанию 0.
- user_low_last_read_seq / user_high_last_read_seq — прочитанные позиции, по умолчанию 0;
  SQL ограничивает их диапазоном 0..last_message_seq, сервис обновляет только через GREATEST.
- created_at — время создания, now().
- last_message_at — время последнего сообщения; SQL CHECK требует NULL ровно при last_message_seq = 0.

Два индекса активности содержат соответственно user_low_id или user_high_id,
выражение coalesce(last_message_at,created_at) DESC и id DESC. Они поддерживают
курсорную выдачу диалогов, в том числе пустых. Направление DESC отражено примечанием DBML.

### chat.message

- id — серверный UUID сообщения, gen_random_uuid().
- conversation_id — обязательный FK к chat.conversation.id, NO ACTION.
- seq — bigint > 0, порядковый номер в диалоге. UNIQUE (conversation_id,seq)
  обеспечивает порядок и индекс истории.
- sender_user_id — UUID автора без FK к User; Chat проверяет участие автора в диалоге.
- client_message_id — UUID фронта, неизменный при повторных попытках.
  UNIQUE (conversation_id,sender_user_id,client_message_id) предотвращает дубли:
  тот же текст возвращает сохранённое сообщение, другой текст вызывает конфликт.
- body — обычный UTF-8 текст, 1–10000 Unicode-символов, не только пробелы и без NUL.
  SQL проверяет непустоту после btrim пробелов, табуляции, LF и CR и длину <= 10000;
  сервис дополнительно проверяет Unicode-пробелы и корректность UTF-8.
- created_at — время сообщения; SQL default now(), при отправке сервис берёт время БД
  после блокировки диалога и не допускает уменьшения времени активности.

При отправке строка диалога блокируется: сообщение, следующий seq и время активности
сохраняются одной транзакцией. Неуспешная отправка номер не расходует. Отметка прочтения
использует ту же блокировку. unread_count вычисляется только по входящим сообщениям
после своей отметки, отдельной колонки счётчика нет. История выдаётся по seq с before_seq/after_seq;
чтение истории само не обновляет отметку.

User проверяет Bearer-сеанс, активность и подтверждение почты. При открытии диалога и новой
отправке Chat проверяет через User существование/активность собеседника и блокировку в обе стороны.
История остаётся доступна участникам после блокировки. Две системы не образуют распределённую
транзакцию: блокировка, одновременно установленная после проверки, может не остановить эту отправку.

Отдельной таблицы участников, привязки к заявке/проекту, вложений, редактирования и удаления нет.
Down 00008 удаляет всю переписку Chat, не затрагивая остальные схемы.
