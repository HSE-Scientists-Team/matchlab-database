# Модель данных MatchLab

Короткий справочник по таблицам и правилам хранения. Имена таблиц и полей совпадают с DBML. Таблицы аккаунтов и подтверждения адресов принадлежат схеме `users`, жалобы — схеме `support`. Письма отправляются синхронно и не хранятся в БД.


## Сущности

| Таблица | Что хранит |
| --- | --- |
| `user_account` | Учётную запись и обязательный уникальный email для входа (нижний регистр). Пароль хранится только как хеш. |
| `user_email` | Подтверждённый email аккаунта. Email хранится в нормализованном нижнем регистре; адрес может быть только у одного аккаунта. |
| `registration_request` | Заявку до создания аккаунта: нормализованный email, хеш пароля, хеш токена, срок действия. Одна текущая заявка на email, без внешнего ключа на аккаунт. |
| `media.file` | Метаданные файла и состояние, владелец, публичность, bucket/key. Байты находятся в приватном S3 bucket. |
| `media.multipart_upload` | Одна multipart-сессия на файл: upload ID, размеры, срок и manifest завершения; прогресс читается из S3. |
| `trusted_email_domain` | Разрешённые домены организаций для регистрации. |
| `project` | Проект, его владелец, описание, сроки, жизненный цикл и результат модерации. |
| `project_position` | Роль в проекте: описание, число мест и дополнительные требования в JSONB. |
| `project_position_skill` | Навыки, нужные для роли, в виде отдельных строк для поиска. |
| `project_tag` | Теги проекта в виде отдельных строк для поиска. |
| `project_member` | Участие пользователя в проекте и назначенная роль. |
| `project_join_request` | Отклик кандидата или приглашение в конкретную роль; хранит решение и участников действия. |
| `support.support_ticket` | Жалобу на пользователя или проект, автора, назначенного сотрудника и состояние рассмотрения. |
| `support.support_ticket_attachment` | Связь жалобы с файлом Media по `file_id`; URL и метаданные остаются в `media.file`. |
| `chat_conversation` | Диалог. Может быть привязан к отклику или приглашению; без такой ссылки — обычный диалог пользователей. |
| `chat_participant` | Участники диалога, время последнего прочтения и архивирования для каждого участника отдельно. |
| `message` | Сообщение в диалоге, автор, текст, вложения и отметки редактирования/удаления. |
| `notification` | Уведомление пользователя, его тип, данные и время прочтения. |


## Связи
- У пользователя одна запись профиля и одна запись настроек приватности. У аккаунта один подтверждённый email; заявки на регистрацию существуют отдельно до создания аккаунта.
- Email аккаунта уникален без учёта регистра. Заявка на тот же email может быть заменена любым новым запросом регистрации: новый пароль и токен заменяют прежние, старые ссылки недействительны. При подтверждении актуальной ссылки аккаунт и `user_email` создаются атомарно, заявка удаляется. Существующий аккаунт регистрация не изменяет. Хеш токена хранится в `registration_request`, срок действия — 30 минут. Подтверждение и замена заявки сериализуются по email; новая заявка не может изменить аккаунт, если подтверждение уже завершилось.
- Пользователь может создать много проектов. У проекта есть роли (`project_position`), теги (`project_tag`), участники (`project_member`) и заявки/приглашения (`project_join_request`). У ролей есть навыки через `project_position_skill`.
- Заявка относится к одной роли и хранит кандидата и инициатора. На пару «роль + кандидат» создаётся одна запись; повторный отклик или приглашение обновляет её статус и тип. После принятия участник команды записывается в `project_member`.
- Диалог имеет участников через `chat_participant` и содержит сообщения через `message`. Заявка может иметь не более одного привязанного диалога.
- Тикет принадлежит автору, может иметь назначенного сотрудника и содержит ровно одну цель: пользователя или проект. Файлы вынесены в `support.support_ticket_attachment`; один `file_id` нельзя дважды прикрепить к одному тикету.
- Отзыв относится к проекту и автору. Для отзыва о человеке заполнен `target_user_id`; для отзыва о проекте он пуст.
- Внешние ключи сейчас используют `ON DELETE NO ACTION`: связанные записи нельзя случайно удалить каскадом. Идентификаторы пользователей, проекта и файла в Support не имеют межсервисных FK и проверяются соответствующими сервисами. Удаление аккаунта должно проходить через предусмотренный статус `deleted` и отдельную процедуру обезличивания.


## Статусы и типы
- `user_account.status`: `active`, `blocked`, `deleted`. Email подтверждается при создании аккаунта записью в `user_email`. До подтверждения существует лишь `registration_request`, у которой нет статуса аккаунта.
- `project.status`: `draft`, `pending_moderation`, `recruiting`, `active`, `completed`, `cancelled`, `rejected`, `hidden`.
- `project_join_request.status`: `pending`, `accepted`, `rejected`, `cancelled`; `type` — `application` или `invitation`.
- `project_member.status`: `active`, `left`, `removed`.
- `portfolio_item.status` и `profile_credential.status`: `draft`, `pending_review`, `verified`, `rejected`.
- `support.support_ticket.status`: `open`, `resolved`, `declined`.

## JSONB: правила и форма данных
JSONB используем для небольших изменяемых наборов полей, форма которых может развиваться. Основные поля для фильтрации, сортировки, связей, прав доступа и модерации должны оставаться обычными колонками или отдельными таблицами. Файлы в JSONB не кладём — сохраняем ссылку на объектное хранилище.
- `project.data`, например `{"problem":"...","goal":"..."}`: описание проблемы и цели. Тип (`scientific` или `practical`) и сфера находятся в колонках, теги — в `project_tag`, потому что интерфейс фильтрует проекты по ним.
- `project_position.data`, например `{"requirements":["Опыт с Python","2 часа в неделю"]}`: дополнительные требования к роли. Навыки вынесены в `project_position_skill`, число мест и открытость роли — отдельные поля.
- `message.attachments`: список объектов вида `{"url":"...","name":"...","content_type":"..."}`. Файлы размещаются в объектном хранилище.
- `notification.data`: небольшой объект контекста уведомления, например `{"project_id":"...","request_id":"..."}`. Получатель, тип и прочитано ли уведомление — отдельные поля.
Версия формата профиля хранится в `user_profile.schema_version`. При изменении формата `project.data` и `project_position.data` поддерживайте совместимость в коде сервиса. Проверяйте JSON при записи. Не помещайте туда секреты, значения для поиска, дублирующие статусы, счётчики мест или большие списки вложений.


## Важные ограничения и поведение
DrawDB DBML не принимает SQL `CHECK`, поэтому правила ниже нужно проверять в сервисе. При добавлении миграций их также следует закрепить `CHECK`-ограничениями в PostgreSQL, где это возможно.
- `project.type` принимает `scientific` или `practical`; `portfolio_item.type` — `scientific` или `project`.
- `portfolio_item.status` проходит путь `draft → pending_review → verified/rejected`. Ссылка на файл — URL/ключ объекта, не содержимое файла.
- `project_position.slots_count` должно быть больше нуля; сервис проверяет значение, миграция должна добавить SQL `CHECK`. Нельзя принять больше активных участников, чем мест; проверка и создание участника выполняются в одной транзакции.
- На пару «роль + кандидат» есть уникальное ограничение, поэтому повторный отклик или приглашение обновляет существующую заявку. При принятии заявки атомарно создавайте `project_member` и закрывайте другие ожидающие заявки того же кандидата на роль.
- Для сообщения автор должен быть участником диалога. Этот инвариант проверяется сервисом при отправке.
- `review.rating` — целое от 1 до 5; проверка выполняется сервисом и должна быть закреплена SQL `CHECK`. Отзывы разрешены после завершения проекта; сервис должен запрещать повторную оценку одной цели по одному проекту.
- `review.target_type=user` требует `target_user_id`; `review.target_type=project` требует пустой `target_user_id`. Проверяйте согласованность в сервисе и добавьте SQL `CHECK` в миграцию.
- Тикет ссылается ровно на одну цель: пользователя или проект; это закреплено ограничением `support_ticket_one_target`. `subject` и `description` должны оставаться непустыми после `btrim`. Пара `(support_ticket_id, file_id)` во вложениях уникальна. Существование межсервисных идентификаторов проверяется приложением.
- Настройки приватности применяются при выдаче API-ответа: наличие контакта в профиле само по себе не означает, что его можно показывать.


## Как менять модель
1. Сначала обновите `schema/matchlab.dbml`.
2. Синхронизируйте ER-диаграмму в `README.md`.
3. Обновите этот документ, если поменялись сущности, связи или формат JSONB.
4. Изменения в рабочей БД оформляйте отдельными миграциями в репозитории соответствующего сервиса.

## Реализованная схема Media

Миграции backend `00002` и `00003` создают схему `media`; DBML отражает их поля, ограничения и индексы. Другие продуктовые таблицы в модели остаются целевыми и ещё не реализованы миграциями. Служебные таблицы Goose и SQL-отпечатков принадлежат migration runner и не являются продуктовыми сущностями.

Файл проходит `pending → ready`. Проверка HEAD сверяет Content-Type и ожидаемый размер с S3. Отмена multipart переводит файл в `failed`. Только владелец удаляет готовый файл; `deleting` хранит внутреннее намерение, а `deleted` — завершённое удаление. Промежуточное состояние позволяет восстановить операцию после сбоя между двумя системами. Оба состояния скрыты из чтения; публичный API не содержит `deleting`. Запись в БД остаётся, байты удаляет S3 DeleteObject.

Уникальна пара `(bucket_name, object_key)`. Для поиска применяются индекс владельца по времени (DESC), индекс состояния и частичный индекс старых `pending`. `owner_user_id` намеренно не ссылается внешним ключом на таблицу другого сервиса. Значение `is_public` разрешает анонимное чтение через Media, но не открывает сам bucket. ETag не является SHA-256.

Multipart-сессия имеет FK на `media.file`, использует состояния `uploading`, `completing`, `completed`, `aborted`. Manifest частей фиксируется перед завершением, чтобы повтор переживал перезапуск. Размер части — 5 МиБ–5 ГиБ, максимум 10000 частей; `expires_at > created_at`. Частичный индекс просроченных незавершённых сессий поддерживает восстановление. SQL Down удаляет tracking-сессии; незавершённые загрузки в S3 необходимо отменить до отката.


## KAN-38: User ProfileService

- `users.user_profile`: типизированные данные профиля в JSONB и настройки видимости. Создаётся для каждого аккаунта; навыки/интересы индексируются GIN. Значок вычисляется по подтверждённой почте hse.ru/edu.hse.ru, отдельно от достижений.
- `users.achievement`: образование, сертификаты, научные и проектные работы. Файлы ссылаются на Media по ID, без межсервисного FK и постоянных signed URL. Статусы unverified, pending_review, verified, needs_evidence. Редактирование сбрасывает проверку; удаление логическое.
- `users.achievement_decision`: неизменяемая история решений с модератором, версией, снимком проверенных данных, доказательством и комментарием. Владелец не проверяет свои достижения.
- `users.user_block`: направленные блокировки; сервисы сообщений и приглашений проверяют обе стороны. Общие проекты не удаляются.
- `users.project_context` и `users.project_context_member`: минимальный доверенный контекст команды. NULL completed_at означает текущий проект; завершённый снимок неизменяем и позволяет оставить отзыв. Полная модель проекта остаётся отдельной будущей областью.
- `users.profile_review`: один отзыв автора об адресате на завершённый проект. Оба должны быть участниками, оценка 1–5, отзыв о себе запрещён. Средняя оценка вычисляется по отзывам.

Контакты доступны владельцу, текущей команде или публично по настройке; блокировка скрывает их от другой стороны. Флаг видимости участия в проектах сохранён для будущего Projects. Внутренние методы очереди/решений/доказательств требуют роли moderator/administrator и не доступны в Gateway.

Миграция 00005 добавляет точные домены hse.ru и edu.hse.ru без изменения существующих правил. Down удаляет новые данные, но сохраняет доменные правила. Исполняемый SQL находится в matchlab-backend; DBML содержит также будущие сущности, ещё не реализованные в API.
